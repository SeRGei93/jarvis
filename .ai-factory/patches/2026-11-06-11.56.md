# MCP: ${VAR} в URL, пустой allowedHosts и коллизии имён инструментов

**Date:** 2026-11-06 11:56
**Files:** backend/src/domain/mcp-config.ts, backend/src/mastra/mcp/manager.ts, backend/src/mastra/tools/registry.ts, backend/src/mastra/agents/orchestrator.ts, backend/src/admin/api/mcp.ts, docs/mcp.md, .ai-factory/ROADMAP.md, backend/test/domain/mcp-config.test.ts, backend/test/config/settings.test.ts, backend/test/admin/mcp.test.ts, backend/test/mastra/mcp-manager.test.ts, backend/test/mastra/tool-registry.test.ts, backend/test/mastra/orchestrator.test.ts
**Severity:** high

## Problem

Верификация MCP-админки выявила функциональный блокер и несколько пограничных дефектов:

- `parseMcpConfig` отклонял `${VAR}` в `url` с ошибкой `url must include a host`, хотя план и документация обещают подстановку env-переменных и в URL. Админ не мог сохранить/проверить конфиг вида `https://${HOST}/mcp`; `SettingsService` также отбрасывал такой сохранённый конфиг.
- Явно заданный `allowedHosts: []` терялся при нормализации и не доходил до SDK. По семантике SDK пустой список означает «запретить все хосты», а его отсутствие — «без ограничений», то есть получался fail-open.
- При коллизии MCP-инструмента с встроенным имя MCP-инструмента всё равно попадало в `activeTools`; встроенный инструмент с тем же именем становился always-active и обходил gating скилов.
- В новом MCP-коде были INFO/DEBUG-логи, хотя план требует только WARN/ERROR; error-text SDK не редактировал URL с query-секретами.
- Исторические строки ROADMAP продолжали описывать MCP как «только сервер search».

## Root Cause

1. `isHttpServerUrl()` намеренно возвращал `false` для любой строки с `${`, и `parseServer()` использовал его для валидации **сырого** URL. В результате проверка, предназначенная для уже развёрнутого URL, применялась до подстановки. Тесты проверяли `expandMcpConfig` на заранее собранном объекте, поэтому путь `parseMcpConfig` / `SettingsService` не покрывался.
2. `expandMcpConfig()` и `buildDefinitions()` использовали условие `allowedHosts && allowedHosts.length > 0`, не различая `undefined` и явный `[]`.
3. Оркестратор брал `Object.keys(mcpTools)` вместо фактически зарегистрированных MCP-имён, а `activeToolNames()` фильтрует только по `registered`, где встроенный инструмент уже присутствует.
4. Логи и текст ошибок добавлялись по общим конвенциям проекта без сверки с более строгим logging-разделом плана; редактирование URL не было реализовано.

## Solution

- `parseServer()` теперь валидирует копию URL, в которой `${VAR}` заменены на `1` (валидны для host/port/path), и отдельно проверяет схему, наличие хоста и отсутствие userinfo. Итоговый URL по-прежнему проверяется `expandMcpConfig()` после реальной подстановки. Так `${VAR}` можно хранить, а невалидные шаблоны (например, `${SCHEME}://`) и креды в URL отклоняются.
- `allowedHosts` сохраняется, если поле задано, включая `[]`; и в `ResolvedMcpServer`, и в server definition SDK. Добавлено пояснение в `docs/mcp.md`.
- `resolveAllToolsWithMcp()` возвращает `{ tools, mcpToolNames }`; оркестратор передаёт в `activeToolNames()` только реально зарегистрированные MCP-имена. `resolveAllTools()` оставлен как совместимая обёртка.
- Из `McpManager` и admin MCP-роутов удалены новые INFO/DEBUG-логи; остались WARN на отказ сервера/refresh/валидацию.
- `McpManager` редактирует сконфигурированные URL (полный URL, `href`, `origin`) в тексте ошибок SDK перед записью в статус и лог.
- Обновлены `docs/mcp.md` и исторические строки `.ai-factory/ROADMAP.md`.
- Добавлены регрессионные тесты: URL-плейсхолдеры в `parseMcpConfig`, `SettingsService` и admin PUT; `allowedHosts: []`; редактирование URL в статусе; отсутствие активации built-in при коллизии.

## Prevention

- Для каждой поддержанной формы входных данных тестировать **весь путь** (parse → settings → manager), а не только чистую функцию расширения.
- При нормализации опциональных полей различать `undefined` и пустую коллекцию, если у потребителя разные semantics.
- При вычислении «always-active» имён использовать фактически зарегистрированный набор, а не исходный конфиг.
- Сверять новые логи с разделом Logging плана; не логировать URL/заголовки/значения env.
- Проверять, что документация не обещает больше, чем реально проходит через API.
